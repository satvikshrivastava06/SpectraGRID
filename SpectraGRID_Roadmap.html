01 Executive Summary

What you've already built, what this roadmap adds, and the one naming decision to make before you write more code.

What's already validated

You don't need to prove the concept anymore — three assignments already did that work, and the fourth quantified its impact. That's an unusually strong starting position for a "prototype roadmap," and this document treats it as one:

  • The AI use case is defined and defensible — a hybrid architecture (Isolation Forest for unsupervised anomaly detection, TinyML on ESP32 for offline resilience, RAG over Llama 3/Groq for grounded conversational alerts) with real input/output contracts already sketched in JSON.
  • The ESG case is quantified, not asserted — GHG Protocol Scope 2 methodology, a 0.71 kgCO₂e/kWh grid factor, and a baseline-to-target table (32,000 kWh recovered, 21.3t CO₂e avoided, MTTD from 14–21 days to <1 minute) that would survive a grant reviewer's questions.
  • The adoption strategy is stakeholder-mapped — four named roles (Maintenance, Facility Manager, Finance, ESG Office) each with an engagement method and a success KPI, plus a phased budget (₹5,000 → ₹30,000 → SaaS tier) and a risk matrix.
  • The scaling thesis is coherent — "Helio-Twin in a box," train-the-trainer for EPC contractors, federated learning for data sovereignty, and SaaS pricing offset by energy savings.

What this roadmap adds

The blueprint and the SpectraGRID spec both point at the same gap: a mature concept needs a mature engineering substrate underneath it before it can be pitched to enterprise CTOs or accelerators. Concretely, this roadmap:

  • Replaces the naive "expected output" baseline with a real pvlib physics model — the single credibility upgrade your own ESG review flagged as highest-priority.
  • Turns "power low" alerts into explainable root-cause attribution (SHAP-style % breakdown across soiling, inverter trips, grid instability, shading, sensor drift).
  • Migrates from a synchronous Firebase pipeline to an event-driven, hexagonal-architecture backend (Postgres + TimescaleDB, Redis Streams → Kafka) so business logic never has to be rewritten as you scale.
  • Adds the missing enterprise primitives your own blueprint scorecard called out: SRE objectives, disaster recovery, FinOps, MLOps, GitOps, OpenTelemetry.
  • Builds the cinematic Command Center frontend you designed — scoped correctly, as an investor/facility-manager-facing layer that sits alongside the WhatsApp-first interface, not instead of it (more on this tension in §11).
One decision to make now

Pick one name and use it everywhere. "Helio-Twin" is your campus-facing, academic brand — it's on four submitted assignments and has institutional trust. "SpectraGRID" is the more ambitious, investor-facing platform name from the blueprint. Splitting the identity across documents reads as unfinished. Recommendation: keep Helio-Twin as the product name and reserve "SpectraGRID"-style language for the parent-company/platform framing if you incorporate later — but this is your call, not an engineering one.

02 Architecture Overview

Clean/hexagonal architecture wrapped around a physics-informed AI pipeline, driven by events, modeled as a graph.

Layered system (physical asset → decision → action)

Clean / hexagonal architecture

The domain core — the Ghost Generation calculation, the Asset Graph, root-cause attribution logic — must not know whether telemetry arrives from Firebase or Postgres, or whether alerts go out over Twilio or WhatsApp Cloud API directly. Every external dependency sits behind a port (an interface defined by the domain) with a swappable adapter. This is what lets you migrate Firebase → Postgres in Phase 2 (§5, Sprint 6) without touching a single line of the GGI calculation. Concretely: a TelemetryRepository port, a NotificationSender port, a WeatherProvider port, and a ModelPredictor port — each with a today-adapter and a tomorrow-adapter listed in §7.

The Asset Graph (digital twin backbone)

Your blueprint correctly identifies this as the single highest-leverage addition. Everything else — root cause attribution, blast-radius analysis, simulation, cascading-failure detection — depends on modeling the campus as a graph, not a flat list:

Tenant→Campus→Building→Rooftop→Array→String→Panel→Inverter→Battery→Grid Connection

In Phase 2 this is a set of Postgres tables with recursive CTEs for traversal. It only needs to become a dedicated graph store (or a GNN input) in Phase 3, once you're modeling cascading failures across multiple buildings.

Event-driven backbone

Everything becomes an event, not a function call — this is what lets the system scale to multiple campuses without rewriting business logic:

TelemetryReceived→ValidationCompleted→ExpectedEnergyCalculated→GhostGenerationDetected→LossAttributed→TicketCreated→NotificationSent→ResolutionConfirmed→ModelRetrained

Prototype: Redis Streams (Upstash free tier). Growth: NATS JetStream. Enterprise: Kafka — see §14 for exact migration triggers.

08 Security Architecture

Governance isn't an afterthought here — "Algorithmic Trust" is already one of your defined ESG metrics.

Prototype (Phase 1–2)

  • Auth: Supabase Auth issuing JWTs; RBAC enforced at the API gateway, not per-screen.
  • Roles: Maintenance (ticket resolution only), Facility Manager (dashboard + ROI approvals), Finance (read-only cost/ROI reports), ESG Office (read-only carbon ledger + export).
  • Device identity: Each ESP32 gateway gets a unique API key scoped to its site; rotate on suspected compromise.
  • WhatsApp webhook validation: verify the signing secret on every inbound Cloud API webhook before trusting a [Fixed]/[False Alarm] click.
  • Audit log: every AI alert and every human response (fixed / false alarm) is logged immutably — this is your Algorithmic Trust / false-positive-rate metric, not a separate feature.

Enterprise (Phase 3+)

  • SSO via SAML, SCIM for automated user provisioning across partner universities.
  • Hardware attestation for gateway devices at scale (prevents spoofed telemetry).
  • Full audit trail exported to a write-once store for compliance review.
  • Role model extends with Tenant Admin and Regional Operator once multi-campus/multi-region lands (§15).

10 MLOps Architecture

The blueprint's sharpest observation: "current design trains models — enterprise systems manage models." Here's the difference in practice.

The management layer

  • Model registry (MLflow): every version tagged with metrics and deployment date.
  • Drift monitoring: weekly check for weather-pattern shifts, seasonal changes, hardware aging — flagged automatically, not discovered by a confused facility manager.
  • Digital shadow mode: before any model acts autonomously, it runs in shadow — logging what it would have recommended, compared against what the human actually did. This is exactly the mechanism your existing [Fixed]/[False Alarm] WhatsApp buttons already feed; formalizing it into a tracked accuracy/override metric is the whole upgrade.
  • Rollback: if a new model version's false-positive rate jumps (e.g. +20%), auto-revert to the last known-good version. Cheap insurance against a bad retrain silently degrading trust.

11 Frontend & Digital Twin Experience

Two audiences, two interfaces — reconciling your WhatsApp-first adoption strategy with the cinematic Command Center vision.

A tension worth naming explicitly

Your Scaling Strategy deck deliberately differentiates Helio-Twin from "Dashboard-Heavy" enterprise competitors by being WhatsApp-first — precisely because ground staff adoption depends on a near-zero learning curve. The Command Center design brief, by contrast, describes an elaborate 3D mission-control interface. These aren't contradictory — they're for different users. Ground staff never need to see the digital twin; they need a WhatsApp message. Facility managers, investors, and accelerator judges are the ones who need to see the system's intelligence to trust it. Build both, but don't let the cinematic layer become the primary operational interface — that would undo the adoption advantage you already designed.

Tier 1 — Operational layer (ground staff, live from Phase 1)

WhatsApp Cloud API + RAG LLM remains the primary interface for maintenance staff throughout every phase. No 3D, no dashboard login — a message, two buttons, gamified feedback ("You saved 12 kg of CO₂ today").

Tier 2 — Ops dashboard (Facility Manager / Finance / ESG Office, Phase 2)

Next.js + Tailwind, RBAC-gated. KPI cards for GGI, PR, MTTD/MTTR, availability, cost/ROI. Not cinematic — fast, dense, glanceable, the tool a facility manager checks every morning.

Tier 3 — Command Center (investors, accelerators, campus demos, Phase 3)

This is where your design brief applies in full. Scoped as a distinct, demo-oriented surface — not the daily-use tool:

  • Signature moment — Ghost Replay™: reconstructs expected vs. actual generation side by side, root causes emerging as the timeline plays, recovery potential calculated live. This is the single feature most likely to make a judge remember the product — keep it as the centerpiece, not one feature among many.
  • Hero sequence: photon particles traveling to panels, some disappearing (ghost generation), AI tracing the missing energy, causes resolving as a percentage breakdown, recovered energy flowing back — communicates the product thesis in ~15 seconds without requiring anyone to read.
  • Interactive digital twin: Campus → Building → Rooftop → Array → String → Panel, smooth zoom transitions, click-through to efficiency/temperature/RUL per panel.

Tech stack

React Three Fiber + Drei for the 3D twin, GSAP ScrollTrigger for narrative transitions, Lenis for cinematic smooth scroll, custom GLSL shaders for photon/energy-flow/heat-distortion effects, Motion for micro-interactions. This is a Phase 3 build — it depends on the Asset Graph (§2, §9) actually existing as real data, not mock JSON.
